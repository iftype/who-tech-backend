# 0005 레포 싱크: PR 하나는 트랜잭션 하나, 통계는 다시 계산

- 상태: 적용 (2026-10-20, #203 · #205 · #210 · #211)

## 배경

레포 싱크는 GitHub PR을 멤버·기수·제출로 바꿔 저장한다. PR 한 건마다:

- 기존 멤버를 상세 화면용 include(블로그 10·제출 50·Person)로 최대 두 번 읽고, 이전 아이디를 따로 읽었다
- 멤버 upsert → 이전 아이디 교체 → 기수·역할·참여 upsert → 제출 upsert를 **트랜잭션 없이** 실행했다. 중간에 실패하면 멤버만 바뀐 반쪽 상태가 남았다
- 닉네임 통계는 기존 값에 **+1**을 했다. 증분 싱크의 5분 겹침이나 재수집으로 같은 PR을 다시 처리하면 횟수가 부풀었고, 프로필 새로고침은 반대로 최근 50건만 다시 세어 덮어썼다
- 증분 싱크는 1페이지(100건)만 봐서 마감일처럼 몰리면 PR을 놓쳤고, 레이트리밋에 걸리면 리셋까지(최대 1시간) 큐가 멈췄다

## 결정

1. **슬림 조회 + 쓰기 단위 하나**: `db/repositories/sync-write.repository.ts`
   - `findTarget`: 싱크에 필요한 필드만 select (이전 아이디·제출 제목 포함)
   - `applyPullRequest`: 네 단계 쓰기를 `$transaction` 하나로. 실패하면 전부 되돌린다
   - 기수·역할 id는 한 번 싱크하는 동안 캐시하되 **커밋 뒤에만** 넣는다(되돌려진 행의 id를 다음 PR이 쓰지 않게)
2. **통계는 증분이 아니라 재계산**: `computeNicknameStats(모든 제출 제목)`. 같은 입력이면 같은 출력(멱등). 싱크와 프로필 새로고침이 같은 함수를 쓴다
3. **동률이면 지금 닉네임 유지**: PR 제목에 닉네임과 실명을 같이 쓰면 둘이 같은 횟수다. 계산 순서에 따라 실명으로 바뀌거나 오락가락하지 않게 한다
4. **레이트리밋은 짧은 대기만 재시도**(2회·60초 이내), 증분 싱크는 오래된 PR을 만날 때까지 최대 10페이지

## 결과

- 성공 경로의 DB 결과는 그대로: 실제 SQLite 스냅샷을 **옛 코드로 먼저 기록**하고 새 코드가 통과(멱등·동률 규칙으로 바뀐 1건만 의도된 갱신)

## 버린 대안

- **통계 증분 유지 + "이미 있는 제출이면 건너뛰기"**: 제목이 바뀐 PR을 정확히 셀 수 없다
- **싱크 전체를 한 트랜잭션**: SQLite 쓰기 잠금을 몇 분씩 잡아 블로그 싱크·어드민 쓰기가 막힌다
- **BullMQ 같은 외부 큐**: 서버 한 대(메모리 956MB)에 Redis를 더 띄울 이유가 아직 없다. 큐는 메모리 하나로 두고 handler map·TTL로 정리했다
