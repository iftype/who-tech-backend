# 0002 DB는 확장 → 이전 → 축소로 바꾼다

- 상태: 적용 (2026-10-19, #185 · #187 · #188. 허용 목록·일관성 검사는 #186)

## 배경

서버 한 대에 SQLite 한 파일이다. 배포 때 1~3초 끊김 말고는 운영을 멈출 수 없다. 그런데 크루의 이전 GitHub ID가 두 곳에 저장돼 있었다.

- `Member.previousGithubIds`: JSON 문자열 컬럼, 4명
- `PreviousGithubId` 테이블: 2명

검색은 테이블을 읽고 레포 수집은 JSON만 갱신해서, 2명은 옛 ID로 검색되지 않았다. 컬럼을 지우고 테이블로 옮기는 마이그레이션 한 번으로 바꾸면 배포 중간에 옛 코드와 새 스키마가 섞여 깨질 수 있고, 되돌리기도 어렵다.

## 결정

단계를 나누고 각 단계를 따로 배포한다. 어느 단계에서 되돌려도 직전 코드가 동작해야 한다.

| 단계 | 하는 일                                                                      | 이 저장소의 예                                                              |
| ---- | ---------------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| 확장 | 새 구조를 추가만 한다                                                        | 테이블은 이미 있음                                                          |
| 이전 | 쓰기 경로를 하나로 모아 양쪽에 쓴다. 백필 후 일관성 검사 0, 읽기를 새 구조로 | `replacePreviousGithubIds` 단일 경로 + 백필 (#185), 테이블에서 읽기 (#187)  |
| 축소 | 옛 구조를 쓰는 코드를 지운다. 컬럼 삭제는 그다음 배포, 🔒 사용자 승인        | JSON 쓰기 중단 (#188). 컬럼 삭제는 리허설까지 마쳤으나 사용자 결정으로 보류 |

- 운영 DB 복사본으로 리허설한다: `scripts/db-rehearsal/`가 복사본에 마이그레이션·백필을 적용하고 서버를 띄워 API 응답 지문과 `src/db/consistency.ts` 일관성 검사를 남긴다. main과 브랜치의 지문이 같아야 한다
- 데이터를 고치는 작업 직전에는 수동 백업을 남긴다

## 결과

- 이전 ID 불일치 2명 → 0명, 옛 ID 검색이 다시 된다
- 운영 중단 없이 세 번에 나눠 배포(#185·#187·#188). 단계마다 운영 API 지문 27개가 배포 전후 같았다

## 같은 원칙으로 내린 다른 결정

- 상태값 CHECK 제약 대신 허용 목록(`src/shared/domain.ts`) + 일관성 검사: Prisma가 SQLite 테이블을 다시 만들 때 CHECK가 사라진다
- 기수 번호에 FK를 걸지 않음: SQLite 테이블 재생성이 필요하고 운영 위반이 0이라 이득이 작다 → 일관성 검사로 감시
